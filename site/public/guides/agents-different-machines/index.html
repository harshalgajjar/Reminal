Getting agents on different machines to work together

Most people running more than one coding agent end up with the same shape: Claude Code on the laptop, Codex on a build box, maybe something scripted on a third machine. None of them can see each other, and every vendor's answer is subagents inside their own product — which does nothing when the tools come from different vendors with complementary skills.

Why the vendor answer does not cover this

Subagents are real and useful, and they are all in-process. Claude's subagents are Claude. Codex's are Codex. The moment your work spans an image model and a coding agent, or two machines, that mechanism has nothing to say.

There is also no cross-vendor protocol coming that would fix it, because agreeing on one is a commercial question rather than a technical one.

What people do today

Shared files. Agents write to a directory both can read. It works, it is asynchronous, and it loses everything about what the other agent is actually doing right now.

Orchestration frameworks. A supervisor process drives several agents through an API. Powerful, and it requires every participant to be a first-class citizen of that framework — which usually means one vendor.

Message queues and webhooks. Fine for events, poor for the thing you usually want, which is "what is that session doing and can I nudge it".

The terminal as the shared surface

Every one of these agents already works in a terminal. That is the one interface they share, and it needs no agreement from anyone.

If a tool can list live sessions across the machines you own, search their scrollback, read a transcript and send keys into one, then an agent using that tool can read and drive another agent — without the other side integrating anything at all. A Codex session has no idea it is being read; it is just a PTY.

This is what we build (reminal — disclosed). reminal integrate registers an MCP server with whichever agent CLIs you have installed, and they get four tools: list_sessions, search_sessions, read_transcript and send_keys.

reminal integrate

The honest caveat: sending keys into another machine's live shell is powerful and blunt. It reaches only machines you have enrolled yourself, and everything it does is visible in the viewer, but per-session opt-in and an audit trail are not there yet.

Common questions

Can Claude Code and Codex talk to each other?

Not directly — there is no shared protocol between vendors, and each vendor's answer to multi-agent work is subagents inside its own product. What they do have in common is that both run in a terminal, so a shared view of terminals is enough for one to read and drive the other.

What is MCP and does it let agents communicate?

The Model Context Protocol is a standard way for an agent to call external tools. It connects an agent to tools, not agents to each other. Agent-to-agent communication happens when the tool an agent calls happens to expose another agent's session.

Do both agents need the same software installed?

No, if the channel is the terminal. The agent being read does not need to know anything about it — a PTY is just a PTY. Only the side doing the reading needs the tooling.

Can agents on different machines work together?

Yes, provided something gives them a shared view across machines. That is the harder half: coordinating two agents on one box is a process problem, coordinating across boxes is a networking and identity problem.
